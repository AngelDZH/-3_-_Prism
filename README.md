# Интеллектуальный сервис планирования рабочих маршрутов для инженеров

Прототип для хакатона «Лидеры цифровой трансформации», задача «Билайн Бизнес» (Beeline Business).
Регион: **Восток** (Москва). Помощник диспетчера: автоматически распределяет заявки между
бригадами, строит маршруты, показывает их на карте, объясняет решение и умеет перестроить
план при появлении срочной заявки.

---

## 1. Цель и идея

Диспетчер ежедневно вручную распределяет десятки заявок между бригадами, учитывая
квалификацию, транспорт, временные окна и приоритет — вручную это плохо масштабируется и
даёт заведомо неоптимальный результат. Сервис решает эту же задачу автоматически:
строит план через солвер (Google OR-Tools, VRPTW), сравнивает его с наивным
распределением «первый подходящий по порядку» (обязательный бейзлайн из ТЗ, §2.3),
и умеет пересчитать план при появлении срочной аварии в течение дня.

---

## 2. Как запустить

### 2.1. Backend

```bash
pip3 install fastapi uvicorn ortools requests osmnx networkx scikit-learn
cd <папка проекта>
uvicorn api:app --reload --port 8000
```
Проверка: `http://localhost:8000/docs` — должны быть эндпоинты `/`, `/plan`, `/plan-variants`, `/baseline`, `/replan`, `/reassign`.

### 2.2. Frontend

```bash
cd frontend
npm install
npm run dev
```
Открыть `http://localhost:5173`.

### 2.3. Сценарий демонстрации (соответствует §4 ТЗ)

1. Вкладка **«Данные»** → «Построить план» — запускается солвер и бейзлайн параллельно.
   Кнопка **«Показать 3 варианта плана»** запускает солвер трижды с разными стратегиями
   построения начального решения (см. §8.4) — диспетчер видит метрики всех трёх и
   выбирает, какой ему больше подходит (например, меньше пробег vs больше заявок).
2. Вкладка **«План дня»** — таблица сравнения солвер/бейзлайн (выполнено, бригад, пробег,
   число рискованных по времени заявок), список бригад с личным пробегом каждой и
   выпадающим списком «переназначить...» у каждой заявки (недопустимые по навыку/транспорту
   инженеры сразу показаны неактивными в списке). Карта показывает точки, окрашенные по
   бригаде (жёлтая обводка — риск опоздания, см. §13), и **линию маршрута каждого инженера**
   от офиса через все его заявки по порядку — реализует требование ТЗ §2.1.4 «показывать
   маршруты и точки заявок на карте», не только точки.
3. Клик по точке на карте — всплывающее объяснение назначения (навык, транспорт, время
   прибытия, длительность работы, вклад в пробег).
4. Вкладка **«Проблемы»** — список неназначенных заявок с человекочитаемой причиной отказа.
5. Вкладка **«Перепланирование»** — диспетчер сам указывает **время события** (общее поле
   наверху, обязательный параметр по ТЗ §2.4, ранее было зашито на 14:00 — исправлено) и
   выбирает конкретное событие: какую заявку отменить, какой инженер стал недоступен, или
   параметры новой срочной заявки (навык, рядом с какой существующей заявкой) — все три
   типа события из ТЗ §2.4. Пересчёт сохраняет уже выполненное, показывает построчный diff
   «было → стало» и сразу обновляет вкладку «План дня» новым, полноценным планом (не только
   текстовый список изменений). Кнопка **«↺ Вернуть исходный план»** откатывает к состоянию
   до события.

## 3. Архитектура

```
Реальные CSV (Восток, Билайн)
   → обогащение: навык/длительность из нормативов, приоритет, координаты
   → матрица времени в пути (OSMnx, реальные дороги Москвы)
   → React (Данные / План дня / Проблемы / Перепланирование)
        ↕
     FastAPI (api.py)
        ↕
  OR-Tools VRPTW-солвер (explain_unassigned.py)   Бейзлайн (baseline.py)
  Перепланирование (replan.py)
        ↓
  JSON-план + объяснения + метрики
```

**Backend:** Python, FastAPI, Google OR-Tools (`pywrapcp`, VRPTW).
**Frontend:** React (Vite), Leaflet/react-leaflet, тайлы OpenStreetMap.
**Гео:** OSMnx — реальные дороги Москвы, без сторонних платных API (см. раздел 6).
**Хранение:** CSV/JSON — объём (68 заявок, 12 бригад) не требует СУБД.

общественный транспорт (оценка через пешеходное время / 1.6).

## 5. Обязательные ограничения (ТЗ §2.2)

| Ограничение | Как проверяется | Как продемонстрировано |
|---|---|---|
| **Квалификация** | `SetAllowedVehiclesForIndex`/`VehicleVar` — заявка допустима только для инженеров с нужным навыком | 9/7/4 инженера на категорию (connection/local/emergency) |
| **Время** | Начало визита ∈ [окно_start, окно_end]; вся смена ∈ [shift_start, shift_end] | Окончание визита окном не ограничено — только сменой (подтверждено заказчиком на сессии вопросов-ответов) |
| **Ресурс (транспорт)** | Проверка `required_transport == engineer.transport`, если поле заявки заполнено | `REQ_TEST_01` (навык emergency + транспорт bicycle) — гарантированно не назначается; `REQ_TEST_02` (навык local + транспорт pedestrian) — гарантированно назначается `ENG_05`. В 66 реальных заявках поле пустое — в исходных данных Билайна такого ограничения не было ни разу |

## 6. Длительность работы: официальный норматив, а не допущение

Таблица `Нормативы.xlsx` даёт норматив 100 минут на аварию (20 дорога + 80 работа) и
аналогично для остальных типов. Мы разбили норматив на два независимых компонента:

- **Длительность работы на объекте** (без дороги) — из `Нормативы.xlsx`: Подключение — 70 мин,
  Авария — 80 мин, Дозаказ — 20 мин, Локальная — 30 мин.
- **Время в пути** — считаем не усреднённым нормативом (20 мин на всех), а **реальным**
  расстоянием через OSMnx + буфер 5 минут на парковку/подъезд.

Это прямо подтверждено постановщиком в ответе на уточняющий вопрос:
*«20 минут необходимо для того, чтобы заявка при постановке в график букировала
какое-то время. При распределении 20 минут меняется на реально рассчитанное время
в дорогу. Да, в таком случае можно заменять 20 минут»*.

## 7. Синтетический ростер инженеров — обоснование

В исходных данных (ни в одном из трёх регионов) нет ни одной строки с информацией о
бригадах, их навыках, смене или транспорте — участникам явно разрешено и предписано
смоделировать это самостоятельно (сессия вопросов-ответов, блок 2 и п.3 итогового FAQ).

12 инженеров (в рекомендованном диапазоне 10–15, ТЗ §6), навыки откалиброваны под
**реальный** спрос Востока (37 заявок connection, 21 local, 8 emergency):

| Навык | Инженеров | Заявок на инженера |
|---|---|---|
| connection | 9 | ≈4 |
| local | 7 | ≈3 |
| emergency | 4 | ≈2 |

Смены — ступенчатые (08:00–16:00 … 14:00–22:00), транспорт — с перевесом в пользу
пешехода/общественного транспорта (7 из 12), согласно ответу заказчика: «в реальности
преимущественно пешеходы, которые пользуются общественным транспортом».

## 8. Алгоритм

### 8.1. Бейзлайн (`baseline.py`, обязателен по ТЗ §2.3)

Заявки обрабатываются **в порядке файла**, без сортировки и оптимизации. Для каждой —
первый по порядку инженер, прошедший все 3 проверки. Порядок посещения = порядку назначения.
Результат: **27/68 назначено, 12 бригад, 137.1 км**.

### 8.2. Солвер (`explain_unassigned.py`, Google OR-Tools VRPTW)

- Узлы: депо + 68 заявок. Транспортные средства: 12 инженеров, у каждого свой callback
  времени в пути (в зависимости от его транспорта).
- Целевая функция — трёхуровневая иерархия, подтверждённая заказчиком:
  1. Максимум выполненных заявок (штраф за отказ по приоритету: авария »
     подключение » ремонт/дозаказ — `10 000 000 / 2 000 000 / 500 000`).
  2. Минимум задействованных бригад (`SetFixedCostOfVehicle = 100 000`).
  3. Минимальный пробег (км × 100 как стоимость дуги).
- Поиск: эвристика `PATH_CHEAPEST_ARC` + локальный поиск `GUIDED_LOCAL_SEARCH`, лимит 20 сек.
  Математический оптимум не доказывается — это не требуется по ТЗ.

Результат: **60/68 назначено, 12 бригад, 190.6 км** (3.2 км/заявку против 5.1 км/заявку
у бейзлайна — солвер закрывает более чем вдвое больше заявок, но и заметно эффективнее
на заявку).

**Проверка корректности распределения (мин. бригад, макс. заявок):** используются все
12 из 12 существующих инженеров — это не «жадное» решение, а объективный потолок: в
ростере только 4 инженера умеют `emergency`, только они могут закрыть 9 срочных заявок,
поэтому исключить кого-то из состава без потери покрытия навыка невозможно. Штрафы
в целевой функции выстроены так, что солвер физически не может пожертвовать выполнением
заявки ради экономии на бригаде (`10 000 000` за отказ » `100 000` за лишнего инженера).

**Две последовательные находки в процессе отладки — обе меняли итоговую цифру, обе
задокументированы честно, а не спрятаны:**

1. *Фиктивный возврат в депо.* Изначально пробег считался с учётом возврата каждой
   бригады в офис после последней заявки — хотя ТЗ прямо говорит, что «возвращение
   в стартовую точку после последней заявки не требуется» (§2.4). Это резервировало
   время под несуществующую поездку и давало заниженный результат (58/68, 243.9 км).
   После исправления (км и время дуги «в депо» обнулены) — 66/68, 204.6 км.
2. *Занижение времени последней заявки.* При том же исправлении случайно занулилась
   не только дорога до депо, но и **длительность самой последней заявки маршрута** —
   из-за этого солвер проверял только «старт последней заявки ≤ конец смены», а не
   «старт + длительность ≤ конец смены», и часть планов формально нарушала обязательное
   ограничение по времени (ТЗ §2.2). После исправления (длительность последней заявки
   учитывается, а не дорога до депо) — окончательный, проверенный результат: **60/68,
   190.6 км**. Эта находка была замечена при внешней проверке кода и является примером,
   почему в README фиксируются такие детали, а не только финальные цифры.

### 8.3. Перепланирование (`replan.py`, `/replan`) — все 3 типа события из ТЗ §2.4, параметры задаёт диспетчер

Функция полностью обобщена под параметры (`event_type`, `event_skill`, `cancel_request_id`,
`unavailable_engineer_id`, `cutoff_str` и т.д.) — не зашита под один пример. На фронтенде
диспетчер сам указывает **время события** (обязательный параметр по ТЗ §2.4 — единое поле
наверху вкладки, используется как `cutoff_str` для любого из трёх типов) и выбирает из
выпадающих списков **какую именно** заявку отменить, **какой именно** инженер стал
недоступен, или параметры новой срочной заявки (навык, рядом с какой точкой):

- **Новая срочная заявка** (`event_type='new_request'`) — авария, подключение или
  локальная заявка, окно начинается в момент события.
- **Отмена заявки** (`event_type='cancel'`) — выбранная заявка убирается из оставшегося плана.
- **Недоступность инженера** (`event_type='unavailable'`) — его смена обрывается в момент
  отсечки, все его будущие заявки уходят в общий пул на переназначение.

Механика для всех трёх одна: всё, что уже выполнено до отсечки, исключается из пересчёта
(«заморозка прошлого»); оставшееся — солвер запускается заново с тем же качественным
поиском (`GUIDED_LOCAL_SEARCH`), что и основной план, лимит 10 сек. Ответ `/replan` содержит
не только текстовый `changes` (diff «было → стало»), но и **полноценный `new_plan`** —
фронтенд сразу применяет его к вкладке «План дня» и на карту, а не только показывает список
изменений отдельно от текущего состояния. Кнопка «↺ Вернуть исходный план» откатывает к
плану, сохранённому перед первым событием в этой сессии.

**Отладочная находка:** изначально пробовали ускорить пересчёт «тёплым стартом»
(`ReadAssignmentFromRoutes`) от предыдущего плана — идея была не трогать лишнего.
На практике `ReadAssignmentFromRoutes` стабильно не принимал маршруты как валидные
(без объяснения причины со стороны библиотеки), из-за чего пересчёт тихо скатывался
на заметно более слабую эвристику (`PATH_CHEAPEST_ARC` без локального поиска) и давал
**худшие**, менее логичные результаты (случайные потери заявок, не связанные с событием).
Решение — отказаться от тёплого старта и использовать полный качественный пересчёт
оставшейся части дня.

### 8.4. Несколько вариантов плана (`run_solver_variants`, `/plan-variants`) — бонус сверх MVP

По кнопке «Показать 3 варианта плана» солвер запускается трижды с разными стратегиями
построения начального решения OR-Tools (`PATH_CHEAPEST_ARC`, `SAVINGS`, `CHRISTOFIDES`),
каждый раз с одним и тем же локальным поиском (`GUIDED_LOCAL_SEARCH`). Диспетчер видит
метрики всех трёх сразу и выбирает подходящий — реализует пункт ТЗ §2.5 «сравнение
нескольких вариантов». На практике варианты дают заметно разный компромисс между числом
закрытых заявок и суммарным пробегом — диспетчер может предпочесть вариант с меньшим
пробегом, если для него это важнее, чем закрыть максимум заявок.

## 9. Объяснения (ТЗ §2.1.7, §2.4.2)

Для каждой назначенной заявки: *«навык и транспорт совпали, прибытие HH:MM, работа N мин,
маршрут +X.X км»*. Для неназначенной — причина по цепочке проверок: нет навыка+транспорта
одновременно → нет инженера, который успевает выполнить работу заданной длительности в
пределах своей смены и окна заявки → все подходящие заняты в это время → (редко) не
хватило времени поиска. Вторая проверка сознательно смягчена: инженер допускается, если
есть хотя бы одна позиция старта, где и окно заявки, и его смена, и длительность работы
совместимы — а не только если смена целиком покрывает окно заявки (более раннее правило
было заведомо строже, чем того требует ТЗ, и могло давать неверную причину отказа).
Формулировки короткие, без разворота всей логики солвера по каждой заявке — по прямому
пожеланию заказчика на сессии вопросов-ответов («не портянка объяснений»).

---

## 10. Метрики (ТЗ §2.3, §2.4.2)

Обе обязательные метрики считаются для солвера и бейзлайна: число задействованных
бригад и пробег — суммарно **и по каждому инженеру отдельно** (поле `engineers_summary`
в ответе `/plan` и `/baseline`, видно на вкладке «План дня»).

## 11. Ручное переназначение (`reassign.py`, `/reassign`) — бонус сверх MVP

Диспетчер может через выпадающий список у любой заявки на вкладке «План дня» вручную
перенести её другому инженеру. Backend проверяет все 3 обязательных ограничения (навык,
транспорт, время/смена) и, если перенос допустим, пересчитывает **только** маршруты двух
затронутых инженеров (не весь план заново) методом наилучшей вставки в маршрут.

**Важное наблюдение, полученное при тестировании этой функции:** итоговый план плотно
оптимизирован (60/68, минимум свободного времени у большинства инженеров), поэтому при
переборе **всех** пар «заявка × другой подходящий по навыку/транспорту инженер» рабочих
перестановок находится немного. Это не недостаток функции переназначения — она корректно
и предсказуемо отклоняет попытки, нарушающие ограничения, и это косвенно подтверждает
качество автоматической оптимизации. Проверка на фронтенде двухступенчатая: список
инженеров сразу фильтрует недопустимых по навыку/транспорту (показывает их серым,
«нет допуска»), а совместимость по времени/смене — более дорогая проверка, требующая
реального пересчёта маршрута — проверяется backend'ом в момент выбора и объясняется
всплывающим сообщением, если перенос невозможен.

## 12. Индикатор риска опоздания — упрощённая версия «прогноза опозданий» (ТЗ §2.5)

Для каждой назначенной заявки считается запас времени между прибытием и концом её
временного окна (`slack_min`). Заявки с запасом менее 15 минут помечаются как рискованные
(`risk: true`) — выделяются жёлтым в списке «План дня» и жёлтой обводкой на карте, с
отдельным счётчиком в таблице сравнения солвер/бейзлайн. Это сознательно упрощённая
эвристика вместо полноценного ML-прогноза — соразмерная объёму MVP.

## 13. Известные ограничения прототипа

- **7 реальных заявок (из 68) не назначены плюс 1 намеренная тестовая (`REQ_TEST_01`)** —
  причина не случайна: почти все 7 приходятся на нехватку инженеров с навыком `connection`
  или `local` именно в вечерние часы. Это структурный вывод анализа, а не недоработка
  алгоритма — при реальном внедрении логичная рекомендация — сдвинуть 1–2 смены на вечер.
  Эта находка стала заметнее и точнее после исправления бага с концом смены (см. §8.2) —
  раньше он маскировал часть нехватки, позволяя солверу нелегально продлевать смену.
- **Терминология приоритета** в ТЗ — «Обычная/Срочная» (два уровня), у нас внутри —
  ранг по типу работы (`emergency`→1, `connection`→2, `local`/`equipment_order`→3, три
  уровня). Мы намеренно сохранили это как ранг типа работы: он точнее отражает реальную
  иерархию, которую подтвердил заказчик («Авария → Подключение → Ремонт/Дозаказ»), и оба
  понятия по сути описывают одно и то же — просто другим словом. Штрафы в целевой функции
  (`10 000 000 / 2 000 000 / 500 000`) реализуют именно эту иерархию.
- **Оборудование** не смоделировано — прямо назван необязательным усложнением и
  в ТЗ, и заказчиком на сессии вопросов-ответов.
- **Перепланирование может немного менять расписание** у заявок, не связанных напрямую
  с новым событием — следствие природы локального поиска метаэвристики (`GUIDED_LOCAL_SEARCH`
  не гарантирует одинаковый результат между запусками), не влияет на итоговое качество
  плана (число выполненных заявок, суммарный пробег).
- Время в пути на общественном транспорте — оценка (пешеходное время / 1.6), а не расчёт
  по реальным маршрутам ОТ — прямо разрешено заказчиком («не является обязательным
  требованием или самостоятельной победной фичей»).

## 14. Идеи дальнейшего развития

- ML-модель прогноза длительности визита по истории (вместо фиксированных нормативов).
- Учёт оборудования как дополнительного ресурсного ограничения.
- Полноценный ML-прогноз риска опоздания вместо эвристики по запасу времени.
- Несколько сценариев событий одновременно в одном пересчёте.
- Расчёт общественного транспорта по реальным маршрутам (ОТ-роутинг).
- Устранение стохастичности поиска для margin-заявок (например, детерминированный seed).
